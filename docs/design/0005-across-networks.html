0005 — Cooperators across LANs and the Internet

Make agent location independent of broker location, while retaining durable receipts, exact session identity and explicit approvals. Start with one authoritative broker accessible over HTTPS. Add autonomous site brokers when local progress during a network partition is a requirement.

Proposal against source 2023d3c9f136b5fd1e1d93cabb373c96c5677206. Status: proposed, not implemented. This numbered design records the network architecture options and recommended sequence; relocating it does not approve a topology or supersede existing implemented contracts. No deployment is performed.

1. Proposed decision and scope

Recommended first delivery: Design A, one shared authority with outbound HTTPS clients. Every agent machine keeps its provider process, bridge journal and approval interface locally. A reachable broker owns messages, queues, documents and arrival feeds. The same client works on a local network, across routed LANs, over a private tunnel, or across the public Internet.

The working assumption is one organizational trust domain per bus and no requirement to accept new broker writes while that bus is unreachable. This is an assumption, not a user-confirmed requirement. Design B below is the alternative when each LAN must remain operational independently. Unrelated organizations should initially use separate buses and explicit federation policies.

Network reachability, site autonomy and high availability are separate requirements. HTTPS solves transport; it does not create a route through NAT, make a resource writable during a partition, or replicate the broker. A public or privately routed ingress must be reachable from every participating network. Agent hosts need outbound connections only.

Preserve the current contracts

One session identity per launch; explicit resume; fsync-backed acceptance; per-resource ordering; queue fencing; document CAS; independent arrival cursors; local approval decisions.

Add network contracts

Authenticated enrollment, resource authorization, durable retry identity, endpoint trust, reconnection, bounded admission and observable delivery stages. Remote access must not silently broaden a credential's authority.

4. Design A: one broker, clients anywhere

Process placement

Each managed agent machine runs a local coop runtime containing the existing host adapter, durable bridge journal and private IPC. It initiates the arrival wait loop to the remote broker, durably receives notices, ACKs them, and wakes its exact local provider session. The provider's MCP stdio frontend forwards broker operations through the same remote endpoint. Approval prompts, activation confirmation and resolution use the existing local IPC boundary.

Unmanaged clients may call remote MCP directly. They can read broker data and poll arrivals, but direct HTTP access alone does not create a host runtime or wake a model. A local runtime is required for managed activation. Provider credentials and workspace contents remain local unless an agent explicitly publishes content through an authorized broker operation.

Native RPC is a transport adapter over shared domain handlers. It must not become a second implementation of queue/document semantics. MCP maps to the same authenticated request and durable operation context. The current UDS adapter remains available for local deployments and tests.

Connections and network failures

Use verified HTTPS, pooled connections and at most one outstanding arrival wait per managed binding. Initial tunables: 25-second long polls, 40-second request deadline, ingress response timeout at least 60 seconds, and jittered reconnect backoff from 250 ms to 30 seconds. Reserve connection capacity for lease renewals and approvals-related broker calls so waits cannot exhaust the pool. Recheck token validity and authorization before returning a long-poll result; revocation cancels outstanding waits.

Forward proxies can be supported through explicit profiles. Do not follow credential-bearing redirects to another authority. Resolve only configured endpoints; a message-supplied address cannot cause a broker to dial arbitrary internal hosts. Loss of connectivity changes presence to a connectivity-derived state; it does not retire or re-enroll the agent. Reconnecting preserves identity, subscription, cursor, binding and operation IDs.

5. Identity, enrollment and Internet security

Identity is independent of network address

Use (bus_id, agent_id) for routing and audit. Hostnames and IP addresses are endpoints, not identities; display names remain labels. A remote profile pins the expected bus ID, verified TLS server name and credential issuer. Certificate renewal does not change bus identity. Broker restart changes a process incarnation; restoring stale data or replacing storage must fence old attachment epochs and be an explicit recovery procedure.

A human or device principal is allowed to create a bounded set of agent instances. Each fresh launch creates a new instance; connection retries reuse that launch's stored enrollment proof. An authenticated retry returns the original enrollment, and lost token issuance is recovered through the same proof without logging bearer secrets. Shared OAuth login or machine certificate must never collapse all launched sessions into one agent identity. Explicit resume reuses the instance and the exact provider session binding.

The current MCP authorization specification describes protected-resource discovery and tokens bound to their intended server. The proposal uses that standard for generic MCP integrations while keeping controlled machine enrollment an explicit separate profile. MCP authorization reference.

Authorization in the shared dispatcher

Introduce a trusted AuthContext with principal, instance, bus, roles and resource scope. Validate it before any side effect, including resource creation and arrival subscription. Enforce the same policy through native RPC, MCP and administrative interfaces. Ignore or reject transport identity overrides in JSON bodies. Do not rely on hiding a tool from tools/list as an access-control mechanism.

Default-deny permissions distinguish inbox send/read/ACK, channel publish/read, queue enqueue/claim/complete, document read/update/claim, subscription creation and instance administration. Exact or namespace-bounded resources are resolved before authorization. Cross-instance feed reads and ACKs are denied. Managed feed consumption belongs to the controller capability and its current attachment epoch; the model's ordinary tool capability cannot consume or ACK that feed independently. A new controller attachment fences the previous one, including already-open waits.

Ingress trust and resource bounds

Use TLS with hostname verification, preferring TLS 1.3; disable TLS early data for mutations. A TLS reverse proxy is the first deployment profile, with the broker on loopback on the same machine. A different-machine backend needs TLS/mTLS too. The broker still verifies access credentials; caller-supplied forwarded identity headers are not trusted. TLS protects connections, while the ingress and broker can read payloads; this proposal does not claim end-to-end payload encryption against them. TLS 1.3 and early-data replay considerations.

Allow only configured Host values; validate any supplied Origin against an explicit allowlist and allow absence for non-browser clients. Keep browser cross-origin access disabled unless a deployment needs it. Enforce bounded request and response sizes, connection counts, per-principal concurrent long polls, subscription counts, backlog bytes, publication rate and disk watermarks. Authentication and enrollment attempts have separate limits. Tokens never enter URLs, metrics labels or retained diagnostic payloads. Audit authorization decisions and operation IDs with payload redaction.

Approve each host permission request locally under the existing launch policy. A remote message cannot grant permissions, select a different workspace or provider session, or invoke the host-control socket. The remote interface exposes broker actions; it is not a general remote shell.

6. Delivery and retries under uncertain networks

The critical failure: the broker commits, then the response is lost. A timeout is an unknown outcome. Retrying an enqueue or claim with a fresh request ID can duplicate work or claim another task. JSON-RPC correlation IDs do not supply durable idempotency.

A durable operation contract

  1. Before submission, the client persists a cryptographically random operation_id and canonical semantic request digest. Key scope is the authenticated principal/instance, bus and operation identity; token renewal does not change it.
  2. The authoritative commit records the operation identity and reconstructible result together with the domain mutation. Identical retries return the original receipt. A reused key with different semantic input returns IDEMPOTENCY_CONFLICT.
  3. An in-flight duplicate joins the existing outcome. After restart, replay rebuilds the receipt index from committed evidence. A separate in-memory cache or a WAL written only after the domain event is insufficient.
  4. Multi-log effects use source-embedded durable intent and destination dedupe, with explicit reconciliation. Each method defines which durable effects its success receipt promises. Registry changes store their retry proof atomically with the registry mutation. Crash gates must demonstrate receipt reconstruction for each method family.
  5. If the outcome cannot be proved, return OUTCOME_UNKNOWN with the operation ID. A status query cannot equate temporary absence with proven non-execution. Retry only with that same ID; do not issue a replacement operation automatically.
  6. Advertise the receipt retention policy. Keep replay tombstones after result compaction, or require a server-issued validity epoch so expired IDs are rejected. Never garbage-collect a key and later execute its delayed retry as new work. Capacity exhaustion rejects new admissions before commitment.

This is at-least-once transport plus idempotent broker effects within the declared operation scope. It does not make arbitrary provider tools or external systems execute exactly once. HTTP's retry rules explicitly require a way to establish safe semantics before retrying a non-idempotent request. RFC 9110 §9.2.2.

What an acknowledgement means

broker_committed means the authoritative broker persisted the promised effect. It does not mean the recipient read it. bridge_received means the local bridge journal is durable before arrival ACK. agent_observed and resolved retain their existing separate meanings. If the runtime is offline, the broker retains notices within advertised quotas; overflow is visible and never silently discards accepted obligations.

For ordinary direct messages, the client persists its processed cursor before ACK and explicitly supplies it after restart. Broker ACK state is currently volatile and can temporarily restore backlog after replay; the receiver must resubmit its saved ACK. Durable broker-side direct-message ACK is a separate migration if that behavior is unacceptable. Neither cursor scheme makes a consumer's external side effect atomic with ACK.

Leases, ordering and clocks

The resource-owning broker decides lease validity; clients renew before expiry with margin for the configured latency budget. During a partition, a client cannot assume its lease remains valid. Stale completions fail the fence check. An already running provider turn may continue locally, so safe checkpoints and downstream fencing remain necessary. Ordering is per authoritative log/resource; there is no global order across buses or inboxes. Presence is advisory, not permission to reassign an exact session.

Remote requests carry a submission deadline separately from message TTL. Expired new operations are rejected; an already committed operation still returns its original receipt. Design A does not silently spool disconnected writes. A future explicit outbox must expose queued_locally separately from broker_committed, preserve the original expiry and bound clock skew.

7. Design B: autonomous LANs and durable forwarding

Each site broker remains the authoritative owner of its local identities and resources. A remote address is a structured tuple such as (bus_id, agent_id), not an arbitrary URL. Peer endpoint mappings and namespace import/export rules are administrator-controlled. Avoid importing another site's registry, tokens or raw JSONL logs.

Forwarding protocol

Start with explicit point-to-point messages and mirrored channel events. Origin acceptance durably records a unique delivery ID, destination bus/agent, original actor, payload digest, authorized route, expiry and outbox obligation. A signed envelope proves the approved origin bus; it cannot assert an identity owned by another bus. Relay and destination dedupe on the origin and delivery ID and reject mismatched duplicate bodies.

Both brokers can initiate outbound HTTPS long polls and uploads to a reachable relay. Direct HTTPS peers are an optional transport optimization when routing permits. Relay receipt is issued only after its durable storage step. Destination receipt is issued only after destination commitment and remains independently recoverable after a lost response. The origin keeps its outbox until destination receipt or an explicit terminal failure/expiry policy; relay receipt alone does not permit declaring delivery.

Expose stages origin_queued → relay_stored → destination_committed → agent_observed → resolved. These are distinct durable or observed facts, not one Boolean. Existing send success must not be relabeled to mean merely queued at the origin; introduce an explicit asynchronous cross-bus send/status contract. Exporting a document version includes its authorized payload or an available owner reference; a remote filesystem blob path is never a usable reference.

Assign route versions and hop limits, prohibit forwarding loops, and bound peer queues and disk use. Preserve the origin's absolute expiry; forwarding never resets TTL. Peer clock skew must stay within an advertised budget; otherwise new expiring deliveries are quarantined or rejected. Already accepted duplicates return their original receipt. Routing, peer-key changes and export grants are audited. A relay is trusted with payload visibility in this first design; confidentiality from the relay would require a separately specified end-to-end envelope/key system.

Do not copy agent_id alone into a new site's identity namespace or allow two sites to concurrently grant a lease for the same logical queue. Moving resource ownership requires an explicit fenced handover with a new ownership epoch. Federation is distinct from replication: losing one site's storage is not repaired merely because another site received some exported messages.

8. Availability, retention and operations

For Design A, keep one active broker and its local root lock. TLS proxies may be replicated, but they must route to that authority; multiple independent writable roots behind a load balancer are invalid. A standby can restore a verified snapshot plus retained logs only after the previous writer is fenced. Asynchronous backup has a nonzero recovery-point risk and cannot promise survival of every acknowledged write after total disk loss.

If automatic failover with zero loss of acknowledged writes is required, Design C must define quorum durability before success, leader epochs, fencing of old leaders, snapshot installation, dedupe-state replication and consistent identity/lease recovery. Do not layer that claim onto the current local-fsync contract. Cross-region quorum latency also changes the write latency budget.

Export metrics for committed RPC latency, commit-to-arrival delay, retries, unknown outcomes, reconnects, rejected admissions, controller epochs, active waits, outbox age, peer lag and receipt/dedupe storage. Distinguish network, broker commit, host admission, model execution and human approval time. Backup/restore includes identities, revocations, subscriptions, receipt/tombstone state and bridge recovery references. No automatic reassignment of a missing provider session.

Profiles should resolve an explicit endpoint selection before inherited environment defaults, with conflicting socket/URL settings rejected. Never put secrets on the command line. Host workspaces and bridge paths remain local even when the broker endpoint is remote. Proposed network profiles are 1, 30, 100 and 250 ms RTT; 0%, 1% and 5% packet loss; 30-second, 10-minute and 24-hour disconnections; and 1, 100 and 1,000 connected instances. Establish feasible load targets before a campaign, including payload sizes, history length and storage medium. TCP loss tests measure delay and retransmission behavior as well as application disconnects. At 250 ms RTT, a round-trip durable reply cannot meet the existing local 10 ms latency target.

For an initial reconnect gate, aim to re-establish a connection within 35 seconds after reachability returns with the proposed 30-second maximum backoff, subject to valid credentials and available service. Treat this as a test target. Queue-drain and delivery delay additionally depend on retained backlog and service rate. Report p50/p95/p99 separately for network overhead, authoritative commit, arrival projection and host admission.

Example: reply lost after enqueue

The client persists operation X. The queue owner commits task T carrying X, then the connection closes before the response. On reconnect the client submits X again. Replay or the live receipt index returns T; no second task is appended. If X is reused for a different payload, it fails. Repeat the same scenario with an owner crash after commit.

Example: managed runtime disconnects after receiving a notice

The local journal contains delivery D but its ACK response was lost. Reconnect uses the same bus, agent and attachment epoch, reissues ACK or re-peeks, dedupes D in the bridge, and reconciles the existing wake. It does not enroll a new instance or start a second provider session.

Example: site B is offline for a day

Under A, B's new broker mutations are unavailable. Under B, B-local queues and documents continue. Messages from A to B remain visibly queued, subject to their original expiry and retention policy. On recovery they are deduped at B; nobody treats relay storage as evidence that B saw them.

12. Decisions before implementation

The principal choice is whether each LAN must accept new local work during an Internet outage. If it must, select Design B as the product destination and build A's transport/security/retry layers as shared foundations. Other sizing inputs are expected sites and concurrent agents, required offline retention, who operates the reachable ingress/relay, and whether different sites share administration or need independent trust policies.

High availability with zero acknowledged-write loss, a hosted multi-tenant service, end-to-end encryption against the broker, and arbitrary offline edits to shared queues/documents each require additional contracts. They are separate decisions rather than implied consequences of supporting TCP.
