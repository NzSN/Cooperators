# Failure and recovery replay contract

[`MBFaults.tla`](../../MBFaults.tla) makes the reviewed obligations usable as
failure-focused tests. It adds explicit inputs, operation outcomes, failure
barriers, crash/recovery steps, and observation projections. Rejected and failed
requests are actions: replay checks their responses and effects.

The [typed fault-profile interfaces](../fault_interfaces/README.md) now use the
model-interface compiler and concrete Rust ports. The generated layer owns the
traits, codecs and dispatch; handwritten methods call actual broker operations
and failure hooks. Model/corpus verification and runtime qualification remain
separate checks. Current implementation evidence is retained under
[`docs/impl/generated-fault-mbt/`](../../../docs/impl/generated-fault-mbt/).

## Follow the existing compiler pipeline

The [gated execution plan](../../../docs/design/0002-generated-adapter-fault-mbt-plan.md)
starts with a generated-port storage pilot and then covers all seven reviewed
defect classes plus the per-launch identity requirement.

The integration extends the reviewed `*.mirror-interface.json`
contracts, resolves a compiler lock, regenerates/checks the Rust port and
binding, and implements its added methods against real fault hooks and
observations. Compiler acceptance of the profile-specific observation shapes
must be verified. Generated files remain compiler-owned.

`contract.json` here uses the separate `cooperators.fault-port/v1` prototype
schema; it is not a Mirrors model-interface contract. `replay_faults.py` is a
standalone Python/NDJSON prototype, not an autogenerated Rust adapter or a
replacement requirement for the established MirrorRust/ModelMirrors pipeline.
The model, traces, authoritative-observation rules, and fault scenarios can feed
that compiler integration; the custom transport does not need to be retained.

Expected rejection/I/O-error outcomes should become explicit generated
observations. Handwritten trait methods record the actual outcome and return
normally to the binding; unexpected adapter failures remain `BindingError`.
The generated layer does not create the Rust failure hooks or repair production
behavior merely from the model.

## Run

From the repository root:

```sh
# Eight safe profiles, 24 fault counterexamples, 24 coverage witnesses.
python3 spec/check_hardening.py --model faults --timeout 60

# Runs the matrix and exports correct-policy witnesses as projected ITF.
PYTHONDONTWRITEBYTECODE=1 python3 spec/mbt/generate_faults.py

# Or reuse the exact complete snapshot printed by the checker.
PYTHONDONTWRITEBYTECODE=1 python3 spec/mbt/generate_faults.py --evidence /tmp/coop-hardening-REPLACE

# Check sources, contract, and every required member; no SUT runs.
PYTHONDONTWRITEBYTECODE=1 python3 spec/mbt/replay_faults.py --verify-only

# Synthetic peers test the tools, not the Rust broker.
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s spec/mbt -p test_fault_tools.py
```

The generator requires complete safe explorations, named fault counterexamples,
all witnesses, matching configurations, and exact source snapshots. It rejects
stale evidence, tool failures, and incomplete runs. The manifest retains model,
dependency, contract, trace, TLC-log, and configuration hashes. No symmetry or
`VIEW` reduction is used. Strict counterexample parsing and projection happen
after safety checking and do not reduce its state graph or evaluate source code.

The generator also drives the original TLA+ `Next` using each trace's fixed
actions and inputs. All twenty-four correct-policy traces must complete with
matching responses/observations. An assigned trace must distinguish each of
the twenty-four faulty policies by an observed mismatch or unexpected deadlock.
This prevents a hidden invariant failure from being mistaken for a replayable
test. Fresh allocation choices are guided only as fixture entropy; reused
identities/tokens and reconnect rebindings are not filtered out. Expected
responses and observations are assertions, not general transition guards.

## Defect-triggering behavior

| Obligation | Trigger and distinguishing observations |
|---|---|
| Root ownership | Competing starts on the same/different sockets; live owners, actual rejection, and durable bytes. An unowned append reaches the protected SUT operation. Handoff preserves records. |
| Write/sync failures | Separate append from sync; partial writes and post-write sync errors leave uncertain bytes. Further append attempts explicitly return `recovery-required` until recovery. Successful receipt IDs and sequences survive. |
| Expired inbox capacity | Fill a two-record inbox and observe `full`; expire messages with a controlled clock; wait returns an advancing cursor without live messages; acknowledge it and send again. |
| Dead letters | Separate durable termination, projection append, and completion. Recover after failure/restart; crash after append and retry without duplicating the terminal's dead record. |
| Initial publication | Create a file before version 1, then fail or crash. Retry the same name and verify readable version 1. Success requires a committed version. |
| Status | Append a record larger than the tail window; compare the reported head with real records and require a read-only observation. |
| Rotation/cursors | Separate segment preparation from commit; preserve ordered records and cursors through rotation/crash. An oversized record occupies a segment alone; the next append rotates. |
| Instance identity | Enroll same-kind/same-display launches with distinct IDs/tokens; retry the initial enrollment; reconnect and rotate without changing ID; reject stale enrollment keys and revoked credentials; retire and allocate a different identity for a fresh launch. |

The 24 bad policies are mutation controls, not 24 additional confirmed Rust bugs.
They cover unsafe ownership/replay, continued I/O after failure, early/wrong
receipts, lost acknowledged data, stalled expiry cursors, missing/duplicate
projection, file-based publication rejection, early publication success,
missing/mutating status, missing/lossy rotation, incomplete cursor reads, merged
or changed/reused identities, unstable retries, stale enrollment acceptance,
shared tokens, and accepted revoked credentials.

## Per-launch enrollment policy

`MBFaults` wraps the abstract lifecycle rules with the concrete enrollment
credential policy. A launch supplies a fresh random 128-bit secret, which also
serves as its initial credential. The registry persists its hash and canonical
ID. A retry before rotation returns that same ID and credential. Retrying the
original launch key after rotation or retirement returns `conflict` with the
reserved ID; it cannot issue a credential or allocate another identity.
`enrollmentHistory` remembers the first credential, retries and retirement only
to check policy and coverage. It is not an implementation observation.

The eight identity witnesses cover distinct same-kind enrollment, stable
reconnect, revoked-token rejection, initial enrollment retry, stale-key retry
rejection, retired-key retry rejection, a fresh launch after retirement, and
retired-credential rejection. Their concrete port reads actual enrollment/auth
replies and registry bytes, using independent first-issuance bijections for IDs
and credentials. Duplicate real values retain one alias and remain detectable.

The actual two-MCP-process acceptance test additionally checks shared-config
launch provisioning, delivery, dedupe, independent acknowledgments/presence,
foreign task/document lease rejection, token rotation, retirement and explicit
resume after daemon restart. These are implementation acceptance checks in
[`tests/instance_launch.rs`](../../../tests/instance_launch.rs), together with
registry tests in [`tests/instance_identity.rs`](../../../tests/instance_identity.rs).
Delivery/ack/lease behavior is not part of the generated identity profile's
observation; those acceptance results must not be reported as generated
identity-port replay coverage. Registry I/O failure and credential entropy
remain outside this model.

## Observation and injection rules

[`contract.json`](contract.json) specifies each field's authoritative source.
Files/records come from read-only scans; inbox/document results from the broker;
projection copies from the real dead log. Internal phase/quarantine fields need
genuine diagnostic seams. Missing support cannot become a predicted value.

The driver owns receipt history. Successful `sync-ok` replies supply actual
`{id, seq}` receipts. The driver retains them across recovery and adds the ledger
to the comparison; an adapter-supplied history is rejected. Recovered records
are checked against factual successful replies, rather than a presumed log
reconstructed from call order. Durable-prefix and projection-work references
remain internal model state, not claimed filesystem observations.

ID/token renaming uses separate bijections built only from actual backend
replies, checked against observed metadata. Two abstract identities cannot share
one concrete ID or token; one abstract identity cannot acquire a different real
ID unnoticed. Kind/display metadata is compared as well. Partial-record `seq=0`
means a measurable tagged raw fragment, not a valid JSONL record.

Byte fixtures use a 32,768-byte unit. The two-unit status window is 64 KiB;
one- and three-unit encoded records straddle it. Rotation uses a configurable
two-unit threshold. Measure whole encoded records including separators. Padding
valid fixture records is allowed; inventing sizes or rotating files directly in
the adapter is not.

## Standalone prototype protocol

The prototype's `--adapter` option targets its custom NDJSON protocol. This
section documents that experiment, not the required architecture for compiler
integration. The Rust harness now routes `--suite faults` and the expanded
`--suite all` through compiler-generated bindings, independently of this
prototype transport.
Each trace gets a fresh process/fixture. `hello` negotiates
`cooperators.fault-port/v1`, capabilities, and implementation/build identity.
Missing clocks, barriers, failpoints, observations, or enrollment APIs fail
before initialization instead of skipping profiles.

Requests contain only `id`, `op`, and parameters. **Expected responses and
observations are never sent to the adapter.** Replies include the same ID,
actual result, and actual observation; storage completion adds its receipt and
identity operations their backend binding. Sets/functions use ITF `#set`/`#map`;
integers may use JSON integers or ITF `#bigint`.

The driver checks IDs, errors, timeouts, duplicate keys, malformed values, and a
4 MiB line limit. Set/function order is immaterial; sequence order and scalar
types remain significant. Results retain qualification hashes and adapter
stderr. Children stay in the adapter's POSIX process group, terminated after
each trace. A handshake declaration is not proof of production-code provenance:
review the actual port and injection seams.

To close an implementation defect:

1. Extend and resolve the reviewed model-interface contract; generate and check
   the Rust binding. Implement its added trait methods, actual observations,
   and real failure/clock/barrier controls against production code. Missing
   required support must fail qualification rather than skip the scenario.
2. Replay these traces against the faulty implementation and retain actual
   mismatches. A missing capability is a coverage blocker, not a reproduction.
3. Fix the owning implementation paths and make replay pass, retaining source,
   contract, corpus, and build identities.
4. Keep the original protocol/writer replay and hardening liveness checks. Close
   defects only after authoritative implementation replay and relevant existing
   regressions pass.

The focused profiles do not prove unrestricted composition, registry I/O
durability, randomness, token secrecy, or filesystem power-loss behavior.
Enrollment/unaffected protocol primitives retain their abstractions. This new
model is bounded and safety-only: recovery witnesses do not establish fairness
or eventual progress. Existing temporal properties remain separate obligations.
