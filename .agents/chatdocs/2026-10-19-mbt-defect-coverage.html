What the three failing traces show

NoCompeteW1

Start w1, then attempt w2 against the same root using another socket. Expected: w2 rejected. Observed: both writers remain active.

NoCompeteW2

Reverse the startup order. Expected: w1 rejected. Observed: both writers remain active. The defect occurs in either ordering.

NoRejectedRecovery

Inject a torn suffix, then attempt a competing start on the same socket. Rejection occurs, but the suffix is repaired and a recovery record is appended first.

The writer adapter reads actual child state and inbox bytes, including record tags, sequence numbers, hash-chain validity, and torn-tail state. It compares durable bytes before and after rejected startup and checks the responding PID during readiness. It does not infer these observations from the expected model state.

Consequence boundary: the traces detect unsafe admission and startup mutation. They stop at the first mismatch and do not establish downstream message loss or corruption caused by concurrent appenders. The torn suffix is an explicit test fixture, not a naturally observed storage failure.

Why a protocol replay can pass while a defect remains

  1. Model tracePermitted send, claim, update, ack, and restart actions.
  2. Broker callThe in-process adapter invokes real daemon methods.
  3. ObservationAck cursors come from the broker; the abstract log comes from adapter bookkeeping.
  4. ComparisonThe observed structure is compared with the trace's expected state.

The protocol adapter appends to its own abstract log after successful calls and retains that log across daemon reconstruction. It does not rebuild this observation from recovered durable files. A successful call with incorrect persistence can therefore pass until some later action exposes the loss.

The 34 protocol traces also omit rejected-operation probes such as stale fences, wrong document versions, and foreign ownership. Restart coverage reconstructs DaemonState; it is not a power-loss experiment.

The separate composed specification reports 22/22 checks passed: four correct-policy safety profiles, twelve required fault counterexamples, and six reachability witnesses. Its configuration has two same-kind launches and a six-transition budget. Those checks validate the modeled policy within that configuration; the new identity and composed models are not yet connected to implementation MBT replay.

What would expose the missing effects

Each missing scenario needs both a triggering action sequence and an observation taken from the broker or its durable data.

  1. Storage: fail sync after bytes are written, attempt a subsequent append, restart, and verify every successful receipt against recovered records and sequence continuity.
  2. Inbox expiry: fill a small inbox with expiring messages, advance a controlled clock, wait and acknowledge using returned cursors, then verify that a new send can succeed.
  3. Dead letters: fail the dead-log append after the queue's terminal event is durable, restart or retry recovery, and inspect the terminal record and corresponding dead letter.
  4. Document publication: fail the initial publication after the file is created, retry the same document name, and verify that version 1 becomes readable.
  5. Status and rotation: compare status with the full durable head after a large record; cross the rotation threshold and read a complete ordered suffix from a cursor saved before rotation.
  6. Instance identity: start two same-kind clients with shared configuration, observe their actual IDs and credentials, then exercise independent delivery, acknowledgment, dedupe, leases, enrollment retries, reconnects, and token rotation.

These are coverage requirements, not changes implemented by this archive request. A fixed implementation should make the existing writer mismatches pass while the corresponding negative controls continue to detect deliberate faults.
