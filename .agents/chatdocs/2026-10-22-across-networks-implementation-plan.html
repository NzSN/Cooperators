Implementing network support in Cooperators

An ordered plan for design 0005: make the existing broker usable across LANs and the Internet, then add site autonomy when required. Each wave ends with reviewable artifacts and a measurable gate.

Source baseline 2023d3c, plus the current uncommitted design document pinned in provenance. All implementation waves below are planned, not executed. This chatdoc is the proposed execution plan; design 0005 remains the canonical architectural source.

1. Delivery scope and working assumptions

First release: Design A for controlled coop clients. Deliver one authoritative broker reached over verified HTTPS, native CLI and MCP-stdio forwarding, remote managed hosts with local approvals, authorized enrollment and safe mutation retries. Public deployment is gated on N5; intermediate listeners are for disposable private test environments.

The execution default is a shared broker and one organizational trust domain per bus. If offline LAN writes are required, N6 becomes part of the required product delivery; N0–N5 remain its foundations. No answer about offline autonomy has been recorded. The plan can be implemented without treating federation or quorum replication as implicit features of a TCP listener.

Keep public network exposure disabled until authorization, retry coverage, quotas and the selected release's gates pass. The plan changes no provider permission policy and introduces no public shell or host-control endpoint.

N0 — Freeze the executable contracts and baseline

  1. Pin HEAD, dirty source/document hashes, tool versions, Cargo lockfiles, current tests and retained evidence. Identify which historical environment constraints still apply; do not reuse obsolete absolute paths or Git settings from the original machine.
  2. Create a machine-readable method matrix under a proposed spec/network/: for every native and MCP route, record principal, permission/resource extraction, schema version, mutation class, retry identity, authoritative storage, commit point, response reconstruction and retention rule. Include enrollment/status/admin surfaces and private bridge calls.
  3. Fix initial profile choices: same-host TLS ingress, A-controlled first, single bus authority, finite quotas, receipt retention epoch and exact protocol support. Record the offline-autonomy branch without blocking the common foundations.
  4. Audit a complete HTTPS/TLS dependency graph offline in an isolated build directory; select exact pins only after resolution and feature review. Preserve pre-network and pre-arrival executables with source hashes for compatibility controls.
  5. Record reproductions of the gaps: body/header principal mismatch behavior, repeat enqueue, lost claim result, volatile ordinary ACK after restart, and non-loopback Host rejection. Record them as baseline observations, not acceptance failures caused by this plan.

Gate G0: every exposed method is classified; proposed source-format changes have a migration/rollback strategy; baseline commands and test/tool prerequisites are reproducible. Missing cached crates, sockets, tools or provider auth become named environment blockers for their gates. Deliver a small reviewable contract package before editing the write paths.

N1 — Introduce the transport boundary

Files: src/client.rs, src/main.rs, src/mcp.rs, src/server.rs, src/error.rs; proposed src/transport/{mod,uds,https}.rs.

  1. Define an endpoint type and a reusable BrokerClient boundary with request context, deadline and typed transport outcome. Implement the current UDS behavior first and adapt existing callers without changing domain semantics.
  2. Add verified HTTPS, certificate roots, connection pooling, bounded bodies and response decoding, no credential-bearing cross-authority redirects, and explicit proxy settings. Keep connect, TLS, HTTP status, broker error and uncertain-write outcomes distinguishable.
  3. Add the private/test-only /v1/rpc adapter with a method allowlist into the shared handlers; begin with reads and long polls. The planned public deployment still terminates TLS at a same-host ingress. Plain backend HTTP must stay loopback-only in that profile.
  4. Resolve profiles and explicit --endpoint or --socket selection consistently. Reject conflicting settings, never fall back to a local root after a remote failure, and retain legacy local defaults.

Gate G1: existing UDS/embedded behavior and golden MCP transcripts remain correct; HTTPS read/wait works against a real disposable TLS fixture; bad certificates and unexpected redirects fail; long polls cannot exhaust renewal capacity. Automatic mutation retries remain disabled until their N3 method gates pass.

N2 — Establish one principal and one bus identity

Files: registry, server dispatch, MCP auth, paths/migration; proposed src/auth/ and shared policy types. Extend existing identity, enrollment, migration and transport tests.

  1. Add stable metadata for every remote root. Reuse an existing arrival bus ID; reject conflicting metadata. Define an explicit registry feature/version guard before old code can replay or repair new-format logs. Merely connecting a client must not upgrade a root.
  2. Translate verified transport credentials to AuthContext. Local token wrappers and remote ingress share the policy boundary; remote arguments.token/params.token cannot replace it. Enumerate all dispatch routes so an unlisted method is denied.
  3. Implement administrator-approved device/service enrollment, durable launch retry proofs, expiring/renewable instance credentials and revocation. The initial controlled-client profile may use approved provisioned credentials; if mTLS identity is supplied through a proxy, authenticate the proxy and reject spoofed forwarding headers.
  4. Add method/resource ACLs, enrollment quotas, bounded waits/subscriptions/request sizes, exact Host policy, Origin policy and private administration/metrics. Limit response construction before serialization where needed.
  5. Specify revocation's admission boundary and policy epochs. Recheck permissions when returning a long-poll result and fence already-open controller waits. Keep successful historical receipt lookup subject to current authority.

Gate G2: valid isolated principals can perform allowed operations; mismatched body credentials, cross-agent feeds/ACKs and cross-namespace writes are denied before effects. Retirement/expiry/revocation cannot revive an identity. Failed migration is recoverable; old executables refuse upgraded roots without changing bytes. No remote administrative route is accidentally inherited from local unauthenticated dispatch.

N3a — Build the durable receipt framework and one complete pilot

Files: proposed src/operations.rs, client-side operation journal, src/envelope.rs, src/storage.rs, src/inbox_writer.rs, src/messaging.rs.

  1. Define operation identity, canonical semantic digest, schema version, submission deadline, durable outcome reference and original response fields. Exclude rotating credentials and transport correlation IDs from the semantic digest. Scope identity to stable principal/instance and bus.
  2. Persist the operation ID and intent locally before first submission. Keep that same ID through retries and credential renewal. Expose unresolved local operations and a deliberate resume command; a new human/model request is a new operation unless it explicitly resumes an earlier one.
  3. Embed operation proof in the authoritative source mutation, or an atomic registry representation where appropriate. The receipt index is derived, not a separately committed promise that can disagree with the source event. Handle concurrent duplicate requests through one completion.
  4. Implement the first end-to-end pilot with direct sends: durable source metadata, digest-conflict rejection, fsync before publishing the receipt, restart reconstruction, unknown-result lookup, and bounded admission. Retain group-commit cancellation safety and committed-reader visibility.
  5. Add scoped hooks to drop a response after commitment, pause before/after sync, partially write a record and fail the receipt projection. Keep production behavior outside injection builds unchanged.

Gate G3a: identical concurrent/restarted submissions create one committed send and return the original receipt; a changed request under the same ID fails; a lost reply after commit is recoverable. Replayed uncertain bytes are reconciled to a durable result before claiming commitment. Existing inbox batch/crash controls and historical hash fixtures remain valid.

N3b — Cover domain mutations, including empty results

Files: src/queues.rs, src/docs.rs, src/channels.rs, src/leases.rs, operation receipts and conformance schemas.

  1. Apply the framework to channel publish; queue create/enqueue/claim/renew/complete/fail; and document publish/update/claim/renew/release. Persist enough original result information, including fences and expiry, to reconstruct the same result after subsequent state changes.
  2. Define negative/no-effect results. A queue claim that originally observed empty must not claim a newly enqueued task when that same operation is retried. Either persist its terminal outcome under the same admission serialization or classify it as explicitly non-final and require a fresh operation to try again; freeze the choice in the method matrix. Use the persisted terminal-outcome option for the initial claim contract.
  3. Order receipt recovery ahead of evaluating changed domain state, after authentication/authorization. Thus a completed task's duplicate completion returns its prior receipt, while a different operation still checks the current lease/fence.
  4. Audit multi-log transitions such as dead-lettering, TTL metadata, blobs and arrival intent. Store recoverable source intent and dedupe derived effects; do not report all effects durable until the method's defined commitment obligations hold.
  5. Extend MCP mutation schemas with an explicit operation reference where required. Generated request IDs only protect the adapter's retries; they do not dedupe independently issued tool invocations. Generic direct clients must meet the declared idempotency contract before A-MCP acceptance.

Gate G3b: lost responses, concurrent duplicates, semantic conflicts and restart replay pass for every method family. Retried renewal never extends a deadline again; replayed claim receipts do not authorize use of an expired lease. Empty-claim replay, CAS conflicts, claim selection and partial multi-log recovery have independent authoritative observations.

N3c — Close lifecycle, cursor and retention gaps

Files: registry and arrival stores, operation index/retention, client recovery state, status/metrics; extend enrollment, retirement, arrival and storage recovery tests.

  1. Make enrollment, token renewal/rotation, retirement and subscription updates recoverable without retaining plaintext bearer tokens in logs. Freeze how a lost issuance response is recovered using the authenticated launch proof.
  2. Keep ordinary ACK explicitly monotonic/volatile and heartbeat explicitly soft state. Persist direct-message receiver progress locally, reapply ACK after reconnect, and do not generalize those operations into a false durable-server guarantee. Arrival ACK and bridge resolution retain durable semantics.
  3. Expose scoped operation status and unresolved outcome handling. Absence in a partially rebuilt index is not proof of non-execution. Block/reconcile conflicting admissions until authoritative replay is complete.
  4. Specify finite result retention plus durable replay protection. Retain compact tombstones or reject old server-issued validity epochs after compaction. A very late retry must never become a fresh mutation. Enforce storage quotas before new admission.
  5. Exercise normal restart, restored stale snapshots and copied roots. Root locks only protect writers on their own host; deployment/restore procedures must fence the previous authority and controller epoch before serving the same bus identity elsewhere.

Gate G3c: every matrix row has an implemented retry class and restart test; duplicate lifecycle requests cannot recreate/restore retired identities; receipt compaction, log rotation and crash recovery preserve replay protection. The remote mode cannot advertise unsupported mutation capabilities.

N4 — Move managed hosts across the network boundary

Files: src/host/runtime.rs, src/host_cli.rs, src/host/bridge.rs, src/host_control.rs, MCP backend and provider fixtures.

  1. Implement the HTTPS BrokerArrivalClient and use the common client for launcher enrollment, subscription and broker calls. Split remote endpoint/credentials from local workspace, private IPC and journal paths; stop requiring a remote broker root to exist locally.
  2. Persist a server-issued controller attachment epoch alongside the managed binding and validate it on wait/ACK. Reattach only through the intended proof; fence previous controllers, including requests already in flight. Keep frontend and controller capabilities separate.
  3. Preserve journal-before-ACK, exact provider session binding and generation checks. On a lost reply, reconcile the existing operation/wake instead of re-enrolling or blindly submitting another turn.
  4. Handle token renewal, revocation, backoff, proxy timeout and reconnection. Maintain capacity for lease renewal while an arrival poll is outstanding. Treat provider Offline as terminal for that adapter instance.
  5. Keep approvals and resolution/activation IPC local; apply existing per-request permission decisions. A remote notification cannot choose workspace, credential, generation or host session.

Gate G4: deterministic host tests pass over the HTTPS fixture with disconnects before/after receive, ACK, claim and wake acceptance. Broker and controller restart in both orders preserve exact identity; stale controllers cannot consume the feed. Existing buffered-frame, approval and uncertain-submission regressions remain passing.

N5 — Qualify and package the selected release

Files: integration tests, spec/, proposed scripts/qualify_network.py, operator/README documentation and new retained evidence under docs/impl/.

  1. Complete full normal/injection regression, generated binding/compiler checks and real crash controls on the final integrated source. Add bounded network-operation/controller models and generated ports; obtain observations from receipts, raw persisted effects and real process state.
  2. Test actual TLS ingress with separate client/broker machines, routed LANs and distinct NAT/Internet sites. Unit tests, a loopback fixture and a TCP listener alone do not satisfy these topology gates.
  3. Run the selected real provider versions through document arrival, queue adoption, approval, lease-expiry and restart scenarios. Qualify each separately; unavailable Claude credentials cannot be replaced by fake-host success.
  4. Measure performance, quotas, slow consumers, disconnect recovery and storage growth under declared workloads. Publish a capability matrix, tested limits and operator recipes for enrollment, revocation, recovery and certificate rotation.
  5. For A-MCP, separately implement/verify the selected authorization-server integration, metadata/version negotiation, modern list caching/discovery and explicit mutation retry semantics. Keep the existing legacy workaround documented as historical scope.

Gate G5: A-controlled is releasable only for passing deployment/client/provider profiles with sealed evidence and no skipped mandatory gate. A-MCP has its own passing interoperability receipts. Neither release implies autonomous LAN writes, end-to-end payload encryption against the broker, replication or automatic failover.

For the initial operation state machine use unseen → in_flight → committed or terminal_no_effect, with unknown representing insufficient evidence rather than a reset to unseen. A terminal outcome must survive restart if its retry must remain terminal. Permission denial remains subject to current policy and must not leak a saved receipt to a revoked principal.

Define broker admission ordering for renewal, revocation and expiry. A historical successful claim receipt is evidence of that claim's past result, not proof that it is still live. Downstream external effects still need application idempotency or fencing; the broker can reject stale completion but cannot undo a command already executed by a disconnected agent.

Network and load matrix

Start correctness at one client, then 100 concurrent instances; use 1,000 as a separately declared scale campaign. Exercise 1/30/100/250 ms RTT, 0/1/5% packet loss, 30-second/10-minute/24-hour disconnections, connection reset after commit, and broker/controller restarts. Application response-drop fixtures are not a substitute for kernel-level packet-loss and real topology runs.

Retain design 0005's initial 25-second poll, 40-second request deadline, ingress timeout ≥60 seconds, jittered backoff capped at 30 seconds, and 35-second reconnect target under a reachable healthy service. Qualify or revise these explicitly; they are not measurements. Choose payload/history/disk profiles and finite memory/backlog budgets before the campaign. Report p50/p95/p99 separately for RPC, committed feed and host admission. Never apply a 10 ms local latency target to a 250 ms RTT link.

6. Integration, rollout and rollback

  1. Land bounded changes in dependency order. Each wave supplies code, method-matrix updates, focused tests and gate receipts. Review cross-cutting server/MCP/storage edits together before the next wave. The present task creates the plan only; commits and deployment remain separate requested actions.
  2. Protect existing roots. Default local mode remains available. Network root activation is explicit and tested on disposable copies before any user-root upgrade. Older event hashing and the current arrival format remain covered by fixtures.
  3. Stage privately. Use a disposable broker and synthetic data with the real TLS ingress. Enable one scoped client, then multiple identities, then a managed host. Validate data recovery, certificate rotation, revocation and limits before broader access.
  4. Advertise exact capability scope. Only enable mutation families with complete receipt gates. Only list passing provider/client versions in release acceptance; the current historical Claude-auth limitation and modern discovery gap remain until fresh evidence closes them.
  5. Rollback by capability and data version. Before root activation, revert binaries normally. After new-format records exist, disabling remote ingress is safe containment; starting an old binary on that root is prohibited. Use a compatible fix or an explicitly approved restore from a verified pre-upgrade backup, with its data-loss interval stated.

Do not deploy several writable copies of one bus behind a load balancer. The single-root lock is not a cross-machine fencing service. Backups preserve identities, revocations, operation receipts/tombstones, cursors and controller epochs; restoring old state must not make a second live authority.

8. First implementation work package

The next concrete package is N0 plus the UDS-preserving portion of N1: create the method contract matrix; pin source/tool/environment evidence; define endpoint/request/outcome types; adapt the existing UDS client and its callers; and prove local conformance remains intact. In parallel with that reasoning, audit the proposed TLS dependency graph, but integrate HTTPS only after the client boundary has a passing control.

The first end-to-end network milestone is an authenticated read/wait over real TLS. The first durability milestone is a direct send whose committed response is deliberately lost, then recovered after restart with the same operation ID. Those two milestones demonstrate the transport and persistence foundations before broadening to queue/document and managed-host behavior.

The largest uncertainties are method-by-method receipt persistence, empty/negative-result replay, source-format migration, controller fencing and actual provider/network qualification. Keep them as explicit gates rather than hiding them in an optimistic time estimate. No implementation acceptance has been recorded by creating this plan.
