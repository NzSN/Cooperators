Fault-injection port and implementation fixes

The fault-injection port makes a failure reproducible in the real Rust code and reports what happened. The implementation fixes change that Rust code so it behaves correctly when the failure occurs.

Testing work

Build the port

Give the replay driver a way to fail one sync, pause at a crash boundary, advance time, restart the broker, and inspect real records and responses.

Result: a reliable reproduction and measurement tool. A faulty broker can still fail its tests.

Product correctness work

Fix the implementation

Change ownership, append/recovery, inbox, projection, publication, status, rotation, and enrollment behavior in the owning Rust modules.

Result: the real broker satisfies the tested requirements, including when failures are injected.

What “port” means here

A port is a test interface implemented by an adapter executable. Our replay driver launches it and exchanges one JSON message per line through standard input and output. Its behavior is specified by contract.json.

The adapter invokes real Cooperators Rust functions or starts actual broker processes. It translates a model action such as sync-fail into a controlled failure at the corresponding point in the production append path, then returns the real outcome and observations.

For example, a request to the port can look like this:

{"id":3,"op":"sync-fail","parameters":{
  "scenario":"storage","actor":"-","value":0,"mode":"-"
}}

These are replay-interface operation names. They are not existing public broker RPC methods. The port needs real hooks and barriers to pause and resume the normal Rust operation at these stages. A pending model result can mean that the operation has reached a test checkpoint before completion.

Four pieces the Rust port needs
PiecePurposeConcrete example
Failure hookMake one selected operation fail inside its real code path.Return an I/O error from the sync operation after the append has written bytes.
BarrierPause at an exact checkpoint so the crash window is reproducible.Stop after a dead letter is appended and before projection completion is recorded.
Lifecycle and clock controlExercise restart, independent writers/sessions, and expiry.Start two daemons on one root or advance the clock past message expiry.
Observation readerMeasure actual results independently of predicted model state.Read inbox bytes, dead-letter copies, returned cursors, committed versions, and enrollment replies.

A valid port drives the existing implementation. It cannot manufacture a dead letter, invent two distinct IDs, or return a predicted cursor to make a trace pass. Unsupported controls or observations must fail capability preflight.

A suitable implementation can use a separate test binary and test-only I/O, clock, and barrier hooks. Normal production execution keeps fault controls disabled. That wiring is a proposed implementation approach, not functionality already present.

Worked example: sync fails after bytes were written

The current append path writes bytes, calls sync_all(), and advances its in-memory sequence only after sync succeeds. If sync returns an error, the bytes can remain while the handle still has its old sequence. Continuing through that handle can reuse a sequence and cause later recovery to discard an acknowledged record.

The new model chooses quarantine until recovery. The following is the actual generated NoStorageRecovery test sequence, starting after fixture initialization. It is a model test, not a newly executed Rust log.

Building the port implements the pause, injected sync error, restart/recovery control, and independent reads. Fixing storage makes step 3 refuse an unsafe append and makes recovery preserve all acknowledged records.

The paired NoAcknowledgedRecovery scenario first obtains a successful receipt, then injects a partial write and recovers. It verifies that an earlier acknowledgment and a later successful append remain consistent with actual records. The driver keeps receipt history across restart; the adapter cannot supply a replacement history.

What the implementation fixes involve

These changes belong in production behavior. The table describes required outcomes and the current model's proposed policies; it does not claim the changes have been implemented.

AreaProduction behavior to implementPort/test responsibility
Writer ownership
src/server.rs		Acquire root-scoped exclusive ownership before state initialization, log replay, or recovery; hold it for the daemon's lifetime. Contenders using different sockets must still reject.Launch real competing processes and check that rejected starts leave durable files unchanged.
Append/recovery
src/storage.rs		Quarantine an uncertain writer after write/sync failure until reconciliation; rebuild sequence/hash state from recovered data and preserve acknowledged records.Inject partial writes and sync failures, attempt another append, recover, and compare real receipts with real records.
Inbox expiry
src/messaging.rs		Return a safe cursor across scanned expired records so wait followed by acknowledgment can release capacity, without skipping undelivered live messages.Control time, fill a small inbox, check the returned cursor and actual pending count, then send again.
Dead letters
src/queues.rs		Recover outstanding projection from durable queue termination; retry after failure/restart and deduplicate by terminal identity.Fail or crash between terminal append, dead-letter append, and completion; inspect the actual dead log for missing or duplicate copies.
Initial publication
src/docs.rs		Use committed/recovered publication state as the authority. An unfinished file must remain retryable instead of permanently reserving the name.Fail after file creation, retry the same name, and read committed version 1.
Status
src/status.rs		Read the complete final record or use a verified head index, including when a record exceeds the 64 KiB tail window.Create a valid oversized record, invoke actual status reporting, and compare its head with the log.
Rotation
src/storage.rs and log readers		Implement segment rotation, ordered replay, and stable cursor reads through boundaries and crashes; follow the declared oversized-record policy.Configure a small threshold, control the segment-creation crash window, and read from a cursor saved before rotation.
Per-launch identity
src/registry.rs, session provisioning		Enroll each new launch with fresh credentials and an ID; preserve that ID on retry/reconnect; revoke old credentials after rotation.Start two same-kind clients sharing configuration and observe distinct actual identities. The driver rejects synthetic aliases hiding a shared ID.

Per-launch enrollment is an unimplemented requirement. Existing unique-name registrations already issue distinct IDs; two processes deliberately sharing a token still authenticate as the same existing identity. Creating a new session requires the provisioning change, not an ID invented in the test adapter.

How the two pieces close a defect

  1. Wire the real path. Implement the relevant port capability and observation reader. Keep fault controls in test/diagnostic wiring and preserve the normal production code path.
  2. Reproduce the failure. Run the generated scenario against the faulty broker and retain its actual mismatch. Missing capability means the test is blocked; it is not a reproduced defect.
  3. Change the owning Rust code. Apply the appropriate ownership, recovery, cursor, projection, publication, status, rotation, or enrollment fix.
  4. Verify the repaired behavior. Replay the same controlled scenario successfully and keep the original protocol/writer and relevant progress regressions passing. Retain source, contract, corpus, and build identities with the result.

The direct dependency is: model → reproducible test interface → observed implementation failure → code fix → passing implementation evidence. The port supplies the testing interface; the fixes supply the corrected runtime behavior.
