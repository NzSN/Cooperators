Inter-Agent Communication Infrastructure — Design Proposals

Project: Cooperators Date: 2026-10-18 Type: chatdoc (design survey, pre-decision)

1. Context and grounding

This document surveys design options for an inter-agent communication substrate in the Cooperators repository. Repository state at time of writing: greenfield (empty README.md, no source, no docs). The proposals are therefore grounded in the surrounding environment rather than in existing project code:

  • In-process collaboration already exists. The local Codex fork provides plaintext collaboration between agents of one session tree: spawn_agent, send_message, wait_agent, followup_task, interrupt_agent, list_agents, task-path addressing (/root/task1/task_3), fixed concurrency slots. Scope: one orchestrator process, parent-child trees only.
  • A proven localhost-daemon pattern exists. kimi-webbridge drives a real Windows browser via HTTP + WebSocket on 127.0.0.1:10086 from WSL — evidence that a small single-purpose local daemon is an acceptable operational shape in this workspace.
  • Workspace conventions favor auditable artifacts. Append-only JSONL logs, retained receipts, and revision-scoped claims are established practice (e.g. rollout summaries, qualification evidence).
Scope assumption. The proposals target communication between independent agent processes on one machine (multiple Codex sessions, Claude CLI invoked through the host-mode bridge, browser-driven agents, CI bots). Intra-session messaging is already solved; cross-machine networking is deferred as an extension axis, not a v1 requirement.

3. Proposal P0 — Mailbox substrate (files + CLI) substrate

A durable, daemon-free message format and command-line tool. Everything else builds on this.

~/.local/share/cooperators/
  registry.json                 # agent registrations: name, kind, pid, heartbeat
  channels/<name>.jsonl         # append-only channel logs, monotonic seq
  agents/<id>/inbox.jsonl       # per-agent direct inbox
  dead/<id>.jsonl               # undeliverable / expired messages

Each record: {seq, id (uuid), ts, from, to, kind, reply_to, idempotency_key, body, prev_hash} — hash-chained per file for tamper-evidence, mirroring the append-only evidence pattern already used for rollout summaries. A small coop CLI (register | send | poll | watch | ack) makes the substrate usable from any shell, including sandboxed agent shells. Delivery semantics: at-least-once; consumers track cursors; dedupe by idempotency_key.

Pros

  • Zero runtime dependencies; works from any process that can write files.
  • The log is the audit trail — replay, forensics, and evidence export come free.
  • Debuggable with tail, jq, rg.

Cons

  • Polling latency (mitigate with inotify/fswatch in the CLI's watch mode).
  • No presence, leases, or backpressure without a process on top.
  • Home-directory writes may need sandbox escalation from some agents; a repo-local .cooperators/ fallback should be supported.

4. Proposal P1 — Broker daemon + MCP facade recommended core

A single-binary localhost daemon (cooperatorsd) following the kimi-webbridge operational pattern: Unix socket for RPC, optional HTTP+WebSocket on 127.0.0.1 for dashboards and non-MCP clients. It fronts the P0 log with live routing and exposes an MCP server, so Codex, Claude Code, and any other MCP-capable CLI join the bus with a config stanza — no per-tool plugins.

Tool surface (MCP)

register_agent(name, kind, capabilities) -> agent_id, token
send_message(to | channel, kind, body, reply_to?, idempotency_key)
wait_message(cursor, timeout)             # long-poll; the wait_agent equivalent
list_agents()                             # presence via heartbeats
claim_task(queue, lease_ttl)              # work-queue with leases
complete_task(task_id, outcome, receipt)
publish(channel, body) / subscribe(channel)

Internals: in-memory routing indexes over the JSONL log; per-agent cursors; idempotency-key dedupe; heartbeats for presence; leases for safe multi-agent task claiming. Implementation language: Rust (matches the surrounding systems work, single static binary) or TypeScript/Node for faster iteration — decide once P0 settles.

Pros

  • Cross-CLI interop via MCP — the one protocol every target agent already speaks.
  • Near-real-time delivery (long-poll/WS) without giving up the file-backed audit log.
  • Adds the semantics files can't provide: presence, leases, backpressure.

Cons

  • One more daemon to supervise (systemd user unit / launchd / manual).
  • MCP tool naming must not collide with the Codex fork's built-in collaboration tools; namespace everything coop_*.

5. Proposal P2 — Extend the Codex fork cross-session

Add a shared on-disk registry to the fork's existing plaintext-collaboration layer so separate codex processes discover one another and route send_message across sessions, using P0/P1 as the wire.

Pros

  • Zero new protocol for the primary tool; reuses task-path addressing.
  • Smallest diff to daily workflow.

Cons

  • Codex-only: Claude/Kimi/CI agents remain outside.
  • Increases the fork's upstream-merge burden — this workspace already carries a preservation-heavy Codex fork.

Verdict: pursue as a thin adapter over P1, not as the primary mechanism.

6. Proposal P3 — External standards (A2A / NATS) defer

Adopt Google's Agent2Agent protocol or a brokered bus (NATS/Redis Streams) for maximal interoperability with outside ecosystems and multi-machine topologies. Heavier operational and conceptual weight; premature while all agents are local and the message schema is still evolving. Revisit when cross-machine or third-party agent interop becomes a real requirement — the P0 envelope is designed to map onto both.

8. Recommended path

  1. Phase 0 — Contract. Specify and implement P0: envelope schema, directory layout, coop CLI, repo-local fallback root. This freezes the durable contract everything else speaks.
  2. Phase 1 — Broker. Implement cooperatorsd with the MCP tool surface over the P0 log. Onboard one Codex session and one Claude CLI session as the proving pair.
  3. Phase 2 — Adapters. Wire the Codex fork's collaboration layer to the broker (P2) so in-tree and cross-session messaging share one substrate.
  4. Phase 3 — Optional interop. Evaluate A2A/NATS mapping only when an external consumer of the bus exists.
Do not skip Phase 0. Building the daemon before the envelope schema is stable is the main way this project fails; the file format is the long-lived artifact, the daemon is replaceable plumbing.

10. Open questions

  1. Cross-machine scope: confirm deferral, or is Windows-side↔WSL agent traffic a v1 requirement (kimi-webbridge already crosses that boundary)?
  2. Agent roster: Codex + Claude CLI only, or also Kimi browser agents and CI bots from day one?
  3. Identity: is a shared local token enough, or do agents need per-agent keys (matters once agents can claim tasks, not just chat)?
  4. Retention: rotate channel logs by age/size, or keep everything forever as evidence?
  5. Implementation language for P1: Rust (single binary) vs TypeScript (iteration speed).
